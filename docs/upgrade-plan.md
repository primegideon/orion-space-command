# ORION Upgrade Plan — Multi-Model AI Fleet & Live Data Physics

> **Status: All sub-tasks complete and deployed to production.**

## Overview

**Goal:** Strengthen ORION's technical architecture by (1) distributing AI workloads across specialist model providers suited to each agent's task, and (2) ensuring every secondary dashboard view is driven by real, dynamic external data feeds rather than static or derived values.

**Scope:** Eight targeted changes across `frontend/src/` — four new AI provider integrations in existing agent routes, and four new or enhanced API routes for secondary views. The master router, Supabase logging, all existing telemetry-core routes, and the client-side component contracts remain completely untouched.

**Approach:**
- Each AI provider is called via plain `fetch()` (no SDK packages needed) from serverless Node.js route handlers, keeping the bundle lean.
- Every new provider call wraps the existing watsonx call pattern: it tries the new model first; if the key is absent or the call throws, it falls through to the current watsonx path.
- Every new secondary data route is a brand-new file under `frontend/src/app/api/` — no existing route file is modified.

**Implementation Notes:**
- All proposed external endpoints are public, free, and CORS-irrelevant from Next.js serverless routes (no browser CORS applies to server-side fetch).
- `satellite.js` v4.1.4 is already installed. No new npm packages are required.
- The one meaningful rate-limit consideration is NASA NeoWs/DONKI, which ORION already handles with `NASA_API_KEY`; the other feeds (NOAA SWPC, SatNOGS, JPL Horizons, CelesTrak TLE) are open and unauthenticated.
- `GEMINI_API_KEY` (Google AI Studio) and `GROQ_API_KEY` (Groq) must be added to `.env.local`; `WATSONX_MODEL_ARCHIVIST` is an optional override.

## Sub-Task 4 — SGP4 Real-Time Propagation in Constellation View

**Status:** [x] done

### Intent
Create a new API route `/api/tle` that fetches live Two-Line Element sets from CelesTrak's GP data feed for the same 12 curated satellites, then uses `satellite.js` (already installed) to propagate each TLE to the current UTC moment, returning real-time ECI coordinates, geodetic Lat/Lon sub-point, and velocity magnitude. The existing `/api/satellites` route (satcat orbital parameters) is untouched. The `ConstellationFleet` component gains a new expandable detail row or supplementary badge showing live Lat/Lon and velocity, fetched from `/api/tle`.

### Expected Outcomes
- `/api/tle` returns for each satellite: `{ norad_id, name, lat_deg, lon_deg, alt_km, velocity_kms, eci: { x, y, z } }` propagated to `Date.now()`.
- `ConstellationFleet` displays real-time sub-point and velocity alongside existing orbital elements.
- On any CelesTrak TLE fetch failure the route returns what it could; on propagation error for one satellite it skips that entry rather than failing the whole response.
- Cache: 10 minutes (TLEs are valid for days; over-fetching wastes CelesTrak goodwill).

### Todo List
1. Create `frontend/src/app/api/tle/route.ts`:
   - Fetch `https://celestrak.org/SOCRATES/query.php?...` — actually use the GP format endpoint: `https://celestrak.org/SOCRATES/` — use the correct GP/TLE endpoint: `https://celestrak.org/satcat/tle.php?CATNR=<ID>` for each of the 12 NORAD IDs, or prefer the bulk GP/JSON endpoint `https://celestrak.org/SOCRATES/...`. **Correct endpoint:** `https://celestrak.org/SOCRATES/query.php` is wrong — use `https://celestrak.org/satcat/tle.php?CATNR=<ID>` (returns 2-line TLE text) or bulk: `https://celestrak.org/gp.php?CATNR=<IDs>&FORMAT=TLE`. Use the bulk format to minimise requests: fetch all 12 IDs as comma-separated `CATNR` query with `FORMAT=TLE`.
   - Parse the returned TLE text (lines: name, line1, line2 triples).
   - For each TLE triple, call `satellite.twoline2satrec(line1, line2)` then `satellite.propagate(satrec, new Date())` to get ECI position/velocity vectors.
   - Convert ECI to geodetic with `satellite.eciToGeodetic(positionEci, gmst)` where `gmst = satellite.gstime(new Date())`.
   - Return the array as JSON with a `propagated_at` timestamp.
2. Add the `next: { revalidate: 600 }` cache hint on the fetch call.
3. In `frontend/src/components/ConstellationFleet.tsx`, add a secondary fetch to `/api/tle` and merge results by `norad_id`. Display a live-updating `Lat/Lon: [x°, y°] | Vel: [v] km/s` sub-line directly beneath the satellite name/NORAD text — always visible, no expand needed.
4. Add TypeScript types for the `/api/tle` response in the route file and import them in the component.

### Relevant Context
- `frontend/src/app/api/satellites/route.ts` — TARGETS array with the 12 NORAD IDs at lines 14-27; do not modify this file.
- `frontend/src/components/ConstellationFleet.tsx` — data fetch at lines 44-72; table rows at lines 133-168.

## Sub-Task 5 — NOAA DSCOVR Solar Wind Feed in Threat Matrix

**Status:** [x] done

### Intent
Create a new API route `/api/solarwind` that ingests live Bz magnetic field component and proton density from the NOAA DSCOVR real-time JSON feed. The `AdvancedThreatMatrix` component already computes drag and RF risk from Kp; adding raw solar wind parameters (Bz and proton density) allows the Orbital Debris / drag model to distinguish between a quiet Kp=3 period and an actual CME-driven event. This route is strictly additive — no existing code paths are touched.

### Expected Outcomes
- `/api/solarwind` returns `{ bz_nT: number, proton_density: number, speed_kms: number, timestamp: string }` from the most recent DSCOVR data point.
- `AdvancedThreatMatrix` renders a live solar wind panel showing Bz, density, and speed alongside the existing Kp section.
- Cache: 60 seconds (DSCOVR feed updates every minute).
- On fetch failure the route returns a graceful `{ error, bz_nT: null, proton_density: null }`.

### Todo List
1. Create `frontend/src/app/api/solarwind/route.ts`:
   - `GET https://services.swpc.noaa.gov/json/dscovr/dscovr_mag_1s.json` — returns an array of objects with `[time_tag, dsflag, bx_gsm, by_gsm, bz_gsm, bt, density, speed, temperature]` where index order matters. Fetch with 10 s timeout.
   - The last element in the array is the most recent reading.
   - Extract `bz_gsm` (index 6 in the sub-array, 0-based), `density` (index 7), `speed` (index 8) and the `time_tag` string.
   - **Note on array schema:** The NOAA DSCOVR feed format for `dscovr_mag_1s.json` is: each row is `[time_tag, dsflag, bx_gsm, by_gsm, bz_gsm, bt]`. Proton density and speed are in a separate file `dscovr_fc_1s.json`. Fetch both files in parallel and join on `time_tag` or simply use the latest entry from each.
   - Return combined JSON; include `next: { revalidate: 60 }`.
2. In `frontend/src/components/AdvancedThreatMatrix.tsx`, add a `useEffect` fetch to `/api/solarwind` and render the values in a new "Solar Wind" module section within the existing threat matrix layout.

### Relevant Context
- NOAA DSCOVR mag feed: `https://services.swpc.noaa.gov/json/dscovr/dscovr_mag_1s.json` — public, no auth, no CORS issue from serverless.
- NOAA DSCOVR plasma feed: `https://services.swpc.noaa.gov/json/dscovr/dscovr_fc_1s.json` — same format, contains density/speed.
- `frontend/src/components/AdvancedThreatMatrix.tsx` — existing `OrbitalDebrisModule` at line 96 fetches `/api/satellites` and `/api/kp`; the new module is a sibling.

## Sub-Task 7 — JPL Horizons Heliocentric State Vectors in Orbit Viewer

**Status:** [x] done

### Intent
Create a new API route `/api/horizons` that queries the NASA JPL Horizons System REST API for high-precision heliocentric Cartesian state vectors for a requested body (asteroid SPKID). When the user selects an asteroid in `OrbitViewerPage`, the Orbit Viewer will fetch its precise heliocentric position and velocity from Horizons and display them alongside the existing animated SVG diagram, grounding the visual with real ephemeris data.

### Expected Outcomes
- `/api/horizons?spkid=<id>` returns `{ x_au, y_au, z_au, vx_kmps, vy_kmps, vz_kmps, epoch, body_name }` for the requested body at current epoch.
- `OrbitViewerPage` shows a "Real Ephemeris" data panel beneath the SVG canvas when an asteroid is selected, populated from this endpoint.
- If Horizons returns an error or the body is not found, the panel shows a graceful "Ephemeris unavailable" message.
- No caching header is set (each query is for the current epoch; Horizons results are essentially instant).

### Todo List
1. Create `frontend/src/app/api/horizons/route.ts` (GET handler, reads `?spkid=` query param):
   - Build the Horizons API URL: `https://ssd.jpl.nasa.gov/api/horizons.api?format=json&COMMAND=<spkid>&OBJ_DATA=NO&MAKE_EPHEM=YES&EPHEM_TYPE=VECTORS&CENTER=500@10&START_TIME=<today>&STOP_TIME=<today+1d>&STEP_SIZE=1d&VEC_TABLE=2&CSV_FORMAT=NO`.
   - Parse the `result` string from the Horizons JSON response — it embeds the vectors in a fixed-width text block between `$$SOE` and `$$EOE` markers.
   - Extract X, Y, Z (AU) and VX, VY, VZ (km/s) from the first data line after `$$SOE`.
   - Return structured JSON.
2. In `frontend/src/components/OrbitalCanvas.tsx` (or its parent `OrbitViewerPage`), when an asteroid is selected, fetch `/api/horizons?spkid=<nasa_id>` and display the ephemeris values in a stats card beneath the canvas.
3. Map the returned `x_au, y_au` to a visible point on the SVG canvas (scale AU → pixels) so the asteroid's real heliocentric position is reflected in the diagram.

### Relevant Context
- `frontend/src/components/OrbitalCanvas.tsx` — `OrbitalCanvasProps` takes `items: AsteroidItem[]`; each item has `nasa_id` (SPK-ID format e.g. "2465633").
- JPL Horizons REST API: `GET https://ssd.jpl.nasa.gov/api/horizons.api` — public, no auth, no rate limit for reasonable use. COMMAND accepts small-body SPKIDs.
- The `OrbitViewerPage` component (parent) controls which asteroid is "selected" — the fetch logic belongs there.
